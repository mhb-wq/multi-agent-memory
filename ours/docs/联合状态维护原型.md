# 联合状态维护原型

这是共享池的研究原型。`configs/multiuser.json` 已启用联合维护、逐卡即时维护和独立状态检索；直接使用 `Settings` 的旧实验构造仍需显式启用联合维护。新运行配置的 `method` 中可设置：

```json
{
  "joint_state_update_enabled": true,
  "immediate_state_maintenance_enabled": true,
  "joint_candidate_limit": 10,
  "independent_state_read_enabled": true,
  "independent_state_limit": 10,
  "state_similarity_threshold": 0.2
}
```

卡片抽取可返回事项描述 `matter` 和人物角色 `participants`；旧输出不含这些字段仍可读取。开启联合维护后，包括无主体公共卡在内的新卡进入待处理队列。逐卡即时维护开启时，每张卡写入后直接处理这一张，再继续处理同消息后续卡片；失败状态返回 `needs_attention`，原卡及待处理记录保留，重放同一消息可重试，已成功卡不重复执行。也可关闭即时开关，使用显式 Sleep 批量处理。

维护时使用卡片内容和事项描述检索候选旧卡，以独立状态语义向量索引查找候选状态，并保留由候选卡证据关联的状态。新旧卡片的 `participants` 通过已登记用户 ID 或 `control.person_aliases` 中的精确别名映射到候选用户，同名或未识别的提及保留为歧义或未解析，不强行写入某个人。示例：`"person_aliases": {"user_1": ["小李", "李工"]}`。说话者、提及者和受影响用户不自动等同，最终由 `focused_joint` 判断。模型提出是否同一事项、卡片关系及状态操作；程序检查候选身份、状态及证据引用，事务性写入状态、变化快照和卡片判断。旧卡不改写。

独立状态读取为当前问题直接在状态向量索引中做余弦检索，返回的状态必须能够取到所有引用的可见卡，并受独立上限约束；它补充支持卡，不替代原卡片候选。实验路径不用于历史或指定时刻查询。

状态向量复用公共 MemOS 的嵌入模型，独立保存于 SQLite，按空间隔离，以精确余弦逐条扫描。首次检索会为已有状态构建索引，更新后会同步；同步失败会记录问题，下一次检索重新核对并重试，不能静默返回旧向量或退回词面匹配。修改嵌入模型配置时重建向量。阈值 0.2 和 Top-K 只是可配置实验起点，尚未验证最佳值。精确扫描和首次批量建索引在大量状态下的耗时、存储与嵌入费用需要实测。

限制：事项和角色是模型生成的候选，不代表已验证实体或事件同一性。身份解析仅依据已登记姓名和手工配置的精确别名，不会自动学习别名或在新消息到来后自动回溯处理所有旧的歧义人物；歧义提及保存在判断记录中，如果后续卡片检索到旧卡，模型可结合新旧证据提出状态操作，但取决于召回和模型判断。旧卡候选由现有后端检索，存在漏召回；公共卡影响的用户只从卡片已解析人物、被召回的旧卡和状态产生。模型判断仍可能错误，程序验证不证明语义正确。状态历史目前是研究快照，不提供历史时点查询、回滚、并发跨进程版本控制或生产迁移；应使用新运行目录和测试数据，先评估再考虑替换默认流程。现有状态可在首次检索时建立状态索引，但不会自动进入联合维护队列；若要重新计算关系和状态，需从源消息回放。
