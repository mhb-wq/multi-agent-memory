# 2026-10-26 修复记录：GroupMemBench 暴露的宏观问题

对应报告：[`experiments/groupmembench/FINDINGS.md`](../experiments/groupmembench/FINDINGS.md)
验证数据：GroupMemBench Healthcare，42 条真实消息，同一批问题
测试：`pytest tests -q` → **148 passed, 12 subtests passed**（原 140 + 新增 8）

## 1. 候选分配：按相关度 + 每人保底，不再按 subject 顺序截断

**改前**：按 `subject_ids` 顺序把命中塞进字典，再取前 20 条；后序用户永远看不到。
实测 81 张卡里 57% 从未进入选择器，正确答案（User_5）不在候选里。

**改后**（`src/ours_memory/multiuser.py`）：

- 保留 `backend.search` 的相关度分数；
- 每个 subject 先按分数取 `quota = max(2, limit // 有命中的 subject 数)` 条（20/4=5，20/6=3）；
- 剩余名额按全局分数补齐；
- 候选上限仍是 20。

**为什么仍是 20**：用本地 embedding 对 81 张卡的引用文本重排，正确答案排 **第 1 名**（0.816，第二名 0.629）。20 不是瓶颈，分配方式才是。

**验证**：候选分布从 `{User_2:7, User_4:13}` 变为 `{User_2:5, User_4:5, User_5:5, User_6:5}`；正确答案 `present=True`，current 读返回的第一张就是它。

## 2. pending 状态的卡片不再从 current 读里消失

**改前**：`_currently_usable` 要求 State 已 confirmed，导致新决策（缺 `valid_from`）被整体丢弃；`history` 反而能看到。

**改后**（`src/ours_memory/multiuser.py`）：

- 新增读专用判断 `_readable_current`：卡片是证据，pending/unknown/conflict 都保留；
- 只有存在"更晚的、已确认的、不同值"时才隐藏旧卡；
- `check_plan_dependencies` 仍使用严格的 `_currently_usable`，计划授权不放松；
- 读结果新增 `state_status` 字段（confirmed / pending / conflict / unknown），回答提示词要求 pending/conflict 只能作为"未确认/并存说法"表述。

**验证**：42 条复跑中正确答案卡在 current 第一位，`state_status=pending`；回答从"资料不足"变为"存在一个尚未确认的演进方案……"。

## 3. Sleep 按 State 地址分组，并真正执行批量巩固

**改前**：`SleepOnlyCore.finish_task` 每张卡单独调用一次 `state` 提示词，从不调用 `review_changed_state`；`SLEEP` 提示词是死代码，`dirty` 永远不清。

**改后**（`src/ours_memory/multiuser.py`）：

- 先把 `pending_state` 队列按 `state_id` 分组，一组只调用一次 `_update_cards`；
- 一组失败只标记该组，后续组继续（不再 head-of-line blocking）；
- 处理完后调用 `review_changed_state` 做批量复核（历史、冲突、证据包），并清理 dirty；
- 复核异常降级为 `needs_attention`，不拖垮整个 Sleep。

**验证**：42 条复跑中 `state` 调用 5 次、`sleep` 调用 3 次（改前 0 次）；`dirty` 从 3 变为 **0**；confirmed State 从 0 变为 **2**。

## 4. 团队/项目主体

**改前**：团队决定只能写成"某个人的偏好/决定"，旧决策无法被标记替代。

**改后**：

- `ControlPlane` 启动时校验：空间的每个成员（含 team/project）必须已登记在 `principals`，授权管理者也必须登记；
- `ENRICH` 提示词改为"subject 的目标/偏好/资源/约束"，明确 subject 可以是注册的团队/项目；团队决定只有登记了对应 `state_key` 且明确达成一致时才写入 State，否则保留为普通 Card；
- 数据模型不需要新增表：`subject=team` 的卡片共享同一个 State 地址（`user_id` 在事件里就是 subject）。

**验证**：新增 `test_registered_team_subject_owns_one_shared_state`：两个用户写入 `subject=team-x`，得到同一个 `state_id`，第三人可读；未登记的成员在构造 `ControlPlane` 时即抛 `ValidationError`。

## 5. 相对日期与计划时间

**改前**：相对日期完全靠模型自觉，留空就留空；计划类事实的 `valid_from` 被写成会议当天，前一天/后一天都查不到。

**改后**：

- 新增 `src/ours_memory/relative_dates.py`：从 `observed_at` 确定性解析 today/tomorrow、weekday、next/this/last weekday、in N days/weeks、month end，以及中文的今天/明天/后天、本周/下周/上周X、月底；歧义表达（"soon"）返回 None；
- Card 新增 `planned_for`：模型没给时，由程序从引用文本解析；`valid_from` 表示"这句话何时生效"，`planned_for` 表示"安排发生在何时"；
- `plan` 类卡片的 `valid_from` 缺省取 `event_time`（说出口的时间），因此计划在说出后即可见，而不是只在会议当天可见；
- `planned_for` 进入 ENRICH 输出、Card 校验和 `_public_card`，回答模型能看到。

**验证**：`test_plan_gets_scheduled_date_and_is_visible_before_and_after`：`"handoff Thursday"`（锚点 2025-07-15 周二）→ `planned_for=2025-07-17`，`valid_from=event_time`；07-14 读不到、07-16 和 07-20 都能读到。

## 6. `conditions` 卡片不再被静默丢弃

**改前**：`multiuser.read` 里 `not card.get("conditions")`，任何带适用条件的卡片永远进不了候选。

**改后**：与单用户路径一致，判断 `set(card["conditions"]) <= set(request.conditions)`；`ReadBody` 新增 `conditions` 字段，`read()` 新增 `conditions` 参数。

**验证**：`test_conditional_card_requires_matching_conditions`：不带条件读不到，带 `["exam"]` 能读到。

## 8. 留出样本复验（同日 19:00）

同一批 42 条只能证明修复路径生效。为了看泛化，另取两个**从未用过的频道/题目**：

- `knowledge_update_2`（Infection Control Campaign / Infection Surveillance，36 条）
- `multi_hop_10`（Chronic Disease Management / Analytics，34 条）
- 共 70 条消息、110 张卡，问题各 1 道，目标时间 2025-07-28。

**留出样本暴露了两个新问题：**

1. **已 confirmed 的 State 证据仍可能进不了候选**：Sleep 已确认 "Lock it. Event-time plus 5–10m micro-batch…"，但这张卡不在 `read` 返回的 16 张卡里。原因是它不在该 subject 的 4 个配额内，向量排名也没进全局补齐。State 是内部数据，卡不在候选里，回答就看不到"已确认"。
   - 修复：`read` 在配额分配前，先把"confirmed State 的证据卡"注入候选（`_readable_current` 的同源逻辑），保证 confirmed 决策至少有一张卡进入选择器。
   - 新增测试：`test_confirmed_state_evidence_reaches_candidates_despite_quota`。

2. **回答模型忽略 `planned_for`**：卡上已经有 `planned_for=2025-07-27`，回答仍说"消息没有时间戳"。
   - 修复：`ANSWER` 和 `OUTPUT_CHECK` 明确要求日期问题用 `planned_for`（为空才用 `event_time`），并禁止在两者存在时声称"没有时间戳"。

**修复后的复验结果：**

| 题目 | 结果 |
| --- | --- |
| `knowledge_update_2` | 锁定卡排第一、`status=confirmed`；回答"团队已锁定 event-time + 5–10 分钟 micro-batch"，与标准答案一致（措辞不同） |
| `multi_hop_10` | 回答现在明确引用 `planned_for=2025-07-27` 与 `2025-07-28`，但把两个"tomorrow"视为冲突，未给出唯一日期；标准答案是 2025-07-27 |

**新发现（未修）**：同一个问题里出现多个相对截止日期（07-26 的"tomorrow"=07-27，07-27 的"tomorrow"=07-28）时，系统没有"哪个是最终承诺"的规则，只能并列。需要：
- 给 deadline 类事实一个 canonical state（或按 item_id 归并），用时间/确认状态选主；
- 或在回答提示里定义"取最早承诺/取最后一次承诺"的业务规则。

**测试**：`pytest tests -q` → **149 passed**（新增 state 证据注入测试）。

**结论**：留出样本证明两件事——修复确实泛化到新频道；但"修完就不再抽"不成立，换内容仍会暴露新问题。建议继续按频道/题型轮换做小样本，并逐步把"答案正确率、证据命中、旧值错误、拒答、越权"做成固定指标，而不是每次人工看文本。

## 9. 仍未解决 / 下一步

- **卡片碎片化**：一条消息仍会拆成 2–3 张卡（含 "which feels important" 这类片段），需要最小信息量过滤或同事件合并；
- **抽取上下文**：ENRICH 仍只看单条消息，缺少线程/角色/频道上下文，团队 vs 个人的判断仍依赖提示词；
- **性能**：`memos_extract` 仍 7–18 秒/条，`review_changed_state` 每个 dirty state 一次 LLM 调用；大规模前需要批量抽取、并发与缓存；
- **同一问题多个相对截止日期**：留出样本 `multi_hop_10` 里 07-26 的 "tomorrow" 和 07-27 的 "tomorrow" 都进了候选，系统并列两个日期，标准答案只认 07-27。需要按 item_id/State 归并 deadline，或明确"取最早/最后一次承诺"的业务规则；
- **计划时间**：`planned_for` 目前只解析相对表达，显式日期仍主要落在 `valid_from`；下一步可以让模型显式区分 "event_time / planned_for / valid_from" 三个字段并加校验；
- 团队主体目前靠配置约定，尚未提供在线注册团队的管理接口。
