# 联合判断校验与恢复

适用于 `joint_state_update_enabled` 的单卡和批量状态维护。此修改改变记忆系统的实验版本：正式实验必须在同一版本和配置下运行，并记录版本及设置；不能把历史实验视为使用了本机制。

1. 模型请求将卡片和状态的内部编号映射为本次请求有效的 `C1`、`C2`、`S1` 等短编号。只映射 ID 字段及参与者映射键，不改写消息、主张、参与人名称或角色。模型输出经反向映射后，才进行完整检查和存储。
2. 校验失败时，`pending_state.last_issues` 和 `joint_attempt` 记录 `validation_code` 及具体字段路径。例子包括 `missing_fields`、`old_card_not_candidate`、`update_matter_conflict`、`subject_not_candidate`、`state_not_candidate`、`state_subject_mismatch` 和 `invalid_evidence`。校验检查结构和一致性，不代表语义真实性已被证明。
3. 除显式的不确定和截断外，联合判断的格式、编号或一致性错误，以及不可解析 JSON，会把具体错误反馈给同一模型重试一次。修复结果重新执行完整检查；再次失败则保留原卡片与待处理记录，不提交状态。
4. 模型明确给出 `relation=uncertain` 或 `action=uncertain` 时保留待处理，不自动要求其改成确定判断。仅有空关系列表或空操作列表并不足以证明系统识别了所有事实不确定性。
5. 批量输出截断时，原有单卡顺序回退改为整个拆分批次在一个 SQLite 事务中提交。任一卡失败，整批状态、状态索引及决定全部回滚，所有卡片保留待处理。`joint_batch_recovery` 记录卡片顺序、每张的处理结果、回滚与否；回滚时保留模型调用日志和判断尝试记录。旧消息后面已有更新事件时，仍需按顺序重放，不得直接补写旧状态。

## 检查开销和原因

`calls` 表中 `focused_joint` 和 `focused_joint_batch` 的 `is_repair=true` 标识修复调用；`usage` 和 `elapsed_seconds` 分别记录接口返回的 token 和耗时。接口未返回用量时不能把缺失用量当作零成本。服务商的 HTTP 级重试各占一条调用记录。

`objects` 表 `kind='joint_attempt'` 保存关联卡片、每轮成功或错误及耗时；`kind='joint_batch_recovery'` 保存拆分回退的结果。记录不保存完整模型原始输出或源消息，历史实验中仅有合并错误标签的记录无法追溯为更细的原因。

成本指标应与处理质量一起报告：修复调用可能增加 token 和时间，不应仅比较最终待处理数量，还应统计原始失败、修复成功、修复后仍失败、明确不确定、以及批次回滚。
